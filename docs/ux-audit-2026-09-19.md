# UX audit - 2026-09-19

## Scope

This audit covers SQL File Detection Tool 1.1.12 on VS Code 1.137.0 for Windows.
The Marketplace VSIX was downloaded directly, its embedded manifest was verified,
and the same 1.1.12 release was installed into both the normal profile and an
isolated test profile.

The repository was fast-forwarded to `origin/main` at commit `34df8d0` before
testing. The test profile used the committed `data sample` workspace and did not
change Azure resources or retain credentials.

## Resolution

The findings below were fixed after the audit and retested against the packaged
VSIX:

- New selections clear all prior file-derived results before analysis starts,
  and Cancel now reports `Analysis canceled.`.
- Every Azure browser phase has a Close action; Escape also closes it and
  restores focus to **Browse Azure**.
- Safe renderer state survives webview recreation. Storage drafts are persisted
  only after query strings and fragments are removed, and setup fields reach
  shared host state before SQL regeneration.
- The file filter is shared between sidebar and editor surfaces.
- The sidebar Explorer is height-bounded so result tabs remain in the first
  viewport.

The final release suite contains 860 tests: 858 passed, 0 failed, and 2 expected
environment skips. Focused packaged-build retesting repeated sidebar destruction/recreation,
Azure open/close, cancellation, and an in-flight new-window move.

## Priority findings

### P1 - A new file can display the previous file's metadata while busy

**Observed**

1. Analyze `employees.csv`.
2. Start analysis of the 80 MB `relocation-stress.csv`.
3. Switch to Metadata while the status says `Analyzing relocation-stress.csv...`.
4. The panel still shows `csv/employees.csv`, its 50 rows, and its prior schema.

The same stale schema remains after Cancel. The new filename in Explorer and the
old details in the content pane can therefore describe different files.

**Cause**

[`UiController.selectFile`](../src/ui/controller.ts) changes the selected id and
tab, while [`UiController.analyzeSelected`](../src/ui/controller.ts) clears only
`preview`. Prior `metadata`, statements, and schema-derived state remain visible
until the replacement analysis finishes.

**Recommendation**

- On a changed selection, clear all file-derived display state before setting
  `busy`, or bind each result to its file id and hide mismatched results.
- Render a skeleton or an explicit `Previous result for <file>` block if keeping
  old data is intentional.
- After Cancel, show `Analysis canceled` and avoid presenting old schema as the
  selected file's result.

**Acceptance test**

While file B is loading or after it is canceled, no metadata, preview, schema,
or SQL labeled as file B may contain results produced for file A.

### P1 - Signed-out Azure Browse has no exit

**Observed**

The signed-out Azure browser shows only `Connect to Azure`. It hides the standard
layout, exposes no Close button, and has no Escape-key handler. Underlying tab
clicks do not exit the browser. A user who does not want to authenticate cannot
return to the normal tool inside that surface.

**Cause**

The signed-out branch in [`renderAzureBrowser`](../media/webview/main.js) returns
before the identity header containing `azureBrowserClose` is built. The global
keydown handler handles storage URL Enter and file-list navigation, but not
Escape.

**Recommendation**

- Put a visible Close button in every Azure browser phase, including signed-out,
  loading, empty, access-denied, and retryable-error states.
- Let Escape post `azureBrowserClose` and restore focus to Browse Azure.
- Add a renderer test that enumerates every `azure.open` phase and asserts an
  accessible exit action.

### P1 - In-progress edits are lost when a webview is recreated

**Observed**

The sidebar uses `retainContextWhenHidden: false`. Hiding and showing it changed
the target id and preserved host-owned file selection and active tab, but:

- an unapplied storage URL reset to empty;
- a data-source edit hidden before its 250 ms debounce reset to `MyDataSource`;
- a file filter reset from `employee` to empty.

Moving an editor panel between normal groups retained its renderer and drafts.
Moving it into a new window recreated the webview, so the same class of draft loss
is possible there as well.

**Cause**

[`main.js`](../media/webview/main.js) stores `pendingEdits`, filters, collapsed
folders, and Azure search queries only in JavaScript variables. It acquires the
VS Code webview API but does not use `getState` or `setState`.

**Recommendation**

- Persist renderer-only navigation state with `vscode.setState` and restore it
  with `vscode.getState`.
- Send editable field values to host state immediately; debounce expensive SQL
  regeneration separately from state capture.
- Keep the storage URL as an explicit draft in host or webview state until Use
  URL commits it.
- Add hide/show and move-to-new-window tests with a draft present.

### P2 - Two visible surfaces disagree on local navigation state

**Observed**

With sidebar and panel open together, selected file and active tab synchronize
correctly. The sidebar filter can be `employee` while the panel filter is empty.
This is internally consistent with renderer-local state but can look like the two
views contain different file sets.

**Recommendation**

Either share filters and collapsed-folder state, or make their surface-local
nature explicit. Sharing is preferable because the rest of the product presents
the two surfaces as views of one state.

### P2 - Sidebar layout pushes the primary result below the fold

**Observed**

At a 284 px content width in a 1440 px-high VS Code window, the header, action
grid, platform selector, and Explorer consume the visible sidebar. Preview,
Metadata, Schema, and generated SQL are below the initial viewport. With one
file selected, most of the Explorer area is empty while the result remains out
of view.

**Cause**

[`main.css`](../media/webview/main.css) gives both `.layout` and `.file-pane` a
560 px minimum height, then changes the sidebar layout to a vertical flex stack.
The two minimum-height blocks accumulate below the large header.

**Recommendation**

- Override the sidebar file pane to use a bounded height, for example a maximum
  of 30-35 percent of the available viewport, with its own scroll area.
- Remove the sidebar layout minimum height and keep the result tabs visible.
- Compress secondary header actions into an overflow menu in the sidebar while
  retaining direct Browse files and Browse folder actions.

**Acceptance test**

At a 280 x 720 webview viewport with one selected file, the active result tab and
at least the beginning of its content are visible without page scrolling.

### P2 - Cancel has no completion feedback

**Observed**

Cancel stopped the large scan and prevented stale completion from overwriting a
subsequent `sample.csv` analysis. It removed progress without a confirmation, and
the old schema stayed visible.

**Recommendation**

Show a short `Analysis canceled` status or notice, clear mismatched results, and
return focus to the selected file or primary action.

## What worked well

- Host-owned state survived editor-group moves, cover/uncover, sidebar
  recreation, and a new-window move during active analysis.
- The active tab and selected file survived webview target replacement during a
  live 80 MB scan; the result completed with the expected 2,000,010 rows.
- A canceled long scan never overwrote a later small-file result.
- Pending setup edits survived tab changes and normal editor-group movement when
  the panel renderer was retained.
- Applying a URL removed query strings and fragments before generation.
- The 284 px sidebar, 384 px panel, 549 px split panel, and full-width panel did
  not overflow horizontally, although the sidebar has the vertical-layout issue
  described above.
- Keyboard and Current file entry points kept the extension in its existing
  editor group.
- The Azure browser remained read-only and did not expose identity details,
  tokens, or account data to the renderer report.

## Recommended implementation order

1. Add an always-available Azure Close action and Escape behavior.
2. Clear or explicitly label stale file-derived content during analysis/cancel.
3. Persist drafts and renderer navigation state across webview recreation.
4. Add integration coverage for sidebar hide/show and new-window moves.
5. Decide whether filters should synchronize across simultaneous surfaces.

## Test limitations

- Azure interactive sign-in was intentionally not completed because it requires
  user consent and account permissions. The signed-out production surface and
  the repository's Azure auth/browser state-machine tests were exercised.
- VS Code's simple file picker exposed no machine-readable multi-selection state;
  single-file selection was validated live and multi-file behavior was validated
  through controller tests.
- The Explorer folder context item was visible and invoked without an extension
  error, but synthetic right-click kept the prior file as VS Code's selected
  resource. Browse folder and direct folder-controller paths passed.
